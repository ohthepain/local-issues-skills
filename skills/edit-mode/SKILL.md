# Edit mode

Give the user a working feedback mode over the current project's running website. This is a standalone skill for any project with accessible web source; it requires no issue queue or sibling skill. Follow the consuming project's instructions and preserve unrelated work.

## Commands and local setup

- **edit-mode on** enables feedback collection in the current app. Reuse existing local tooling; generate it only on first use and repair it only when needed. Bare **edit-mode** is an alias for on. Repeated on is idempotent: no regeneration, duplicate overlays, or duplicate listeners.
- **edit-mode off** disables the overlay, review UI, listeners, observers, and active gestures without changing product source or deleting feedback. Repeated off is harmless. It does not submit feedback or implement changes.
- **Done** stops collection and opens review; it does not delete local tooling. Return to collection explicitly enables it again.

Inspect project instructions, launch commands, existing preview, browser tools, and any previous edit-mode integration before changing files. Read [the interaction contract](references/interaction.md) before setup or repair. Reuse the running app and existing tooling. Activating known working tooling should be a short toggle, not another implementation task.

Keep the overlay, feedback drafts, and local launcher/config in a clearly named local-only directory outside public/static folders and production input trees. In Git projects resolve the actual worktree exclude path with `git rev-parse --git-path info/exclude`, preserve its contents, and add narrowly scoped entries there rather than changing tracked `.gitignore`. Check whether files are already tracked: ignore rules cannot untrack them. Never stage overlay files, use force-add, or remove tracked files from the index automatically. Approved product edits remain ordinary source changes and are separate from tooling.

Use an existing development hook, a local launcher/config wrapper, or a loopback-only development proxy to load the overlay without persistent edits to tracked app source, package scripts, dependencies, or config. Do not place it in a production entrypoint guarded only by a runtime flag; production builds must not bundle or copy the tooling at all. Local exclusion from Git alone does not ensure build exclusion. If the app has no suitable integration path, explain the constraint and agree on an alternative rather than leaving tracked integration changes behind. For earlier tracked integration, identify the exact tooling changes and remove only separable tooling edits while preserving unrelated work; ask if removal is ambiguous.

Every fresh app launch and full document load starts **off**, even when feedback drafts exist. Keep activation in memory, separate from persisted drafts; do not restore it from storage, cookies, or a sticky URL flag. Same-document route changes can retain the current active state. After full navigation/reload, drafts survive but collection requires explicit on again. A local controller may explicitly activate the page in response to the current on command, but must not auto-enable future launches. Keep a reusable local launch/toggle path so enabling again does not require regenerating code.

Keep normal app controls working. Open the enabled app through available browser tooling and give the user its launch/toggle command or link. If browser control is unavailable, provide a working local path and state what you could not exercise. Do not substitute a simulation without agreement. Installing local feedback tooling is authorized by invoking this skill; requested product changes still need the confirmation below.

## Collect and review

Let the user explore and collect element comments, general complaints, deletion marks, live resize requests, and font family/size/color requests across pages. Resizing changes the actual element live; the bold italic **f** button previews typography on text elements. Keep these previews reversible and restore app styling on Done/off; retain the requests in drafts. Preserve drafts through navigation. Changes collected here are proposals, including gestures; they do not authorize product code edits.

**Done** exits edit mode: stop hover targeting, remove outlines and gesture previews, and open **Review changes** with every request shown beside a checkbox, checked by default. Preserve the feedback drafts. The user can uncheck entries to disregard them, revise feedback, or return to collection. Provide **Confirm and send** to explicitly approve and submit the exact checked requests to the model using an actually available host connection. Send one scoped message containing the session/revision, selected request IDs and details, explicit confirmation, and instructions to implement the approved changes, run relevant checks, and reload the app afterward. With no working connection, provide Copy/export with selectable text fallback and explain that the user must paste the request into chat. Do not assume the webpage can message the chat or that a browser button resumes the model automatically.

Read the selected feedback and relevant source. Resolve target identity against the current app; do not guess when a target has become ambiguous. Turn each selected request into a concrete proposed fix. Ask focused questions for complaints with materially different interpretations. Present the numbered proposals and retain the per-change checkbox selection in the review UI. Confirmation already supplied by **Confirm and send** authorizes clear requests whose implementation matches the confirmed intent; do not ask again for the same scope. If interpretation changes the requested behavior or resolves a material ambiguity, request confirmation of the clarified proposal before editing. If the host cannot connect the review UI to chat, accept numbered selections and confirmation in chat and reconcile them before edits. Export, collection completion, and checkbox selection alone are not approval. Changed proposals or newly checked entries need confirmation before implementation.

## Apply and verify

After confirmation, implement only the approved entries in source. Translate resize intent into suitable responsive styling rather than blindly copying pixel dimensions. Implement approved typography through the project’s existing styling/font conventions; clarify a requested unavailable font before adding an external font resource. Preserve normal behavior except where the approved change specifically alters it. Flag conflicts or unavailable targets instead of silently expanding scope.

Run relevant project checks and inspect the affected app pages with available browser tools. Report what actually passed and what remains unverified. After successful edits and required checks, reload the existing app preview, wait for it to become ready, and inspect the affected page with edit mode off. Restore the reviewed page where practical. Do not treat hot reload alone as a verified reload. If checks fail, report the failure without claiming completion; if browser access is unavailable, give the user the reload link or command and state that automatic reload was not performed. Offer another feedback round. Keep feedback tooling opt-in and out of production builds; disable it when the session is finished and retain the reusable local tooling for the next on command, preserving approved product changes. Do not discard pending feedback without the user's agreement. Commit, publish, and issue-state transitions follow separate project/user authorization.
