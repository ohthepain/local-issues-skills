# Tutorial

Build one focused experience that lets the user perform the actions and judge the result. Inspired by Matt Pocock's prototype approach: answer a concrete question, expose relevant state, and keep disposable code easy to run and remove. This skill is standalone; it requires neither prototype nor local issue skills.

## Choose the evidence

Read the request, any referenced issue or reproduction steps, project instructions, and relevant implementation. Identify the question, starting state, actions, and expected observable results. Resolve only ambiguities that affect the walkthrough; ordinary implementation choices are yours.

Prefer a tutorial over the actual changed application. Use a standalone reproduction or simulation when requested or when real integration is unavailable; visibly label simulated behavior and explain what remains unverified in the real app. A standalone HTML model is useful for state logic; an existing app route is useful for real interactions. Produce one experience, without design variants.

Adding the tutorial does not authorize implementing the underlying fix. Work from the current implementation unless the user also requests a fix. Keep issue status and acceptance under the consuming project's workflow; reading an issue requires no queue initialization.

## Build the walkthrough

Use the project's existing UI and routing conventions. In an app, provide an explicit launch control or URL opt-in, development/preview-only by default. Keep tutorial code clearly named and removable. Give the user a working launch command or file and open the available preview. Preserve authentication and real data behavior; use isolated fixtures where needed.

Start from the beginning state visible when the app first loads, rather than dropping the user into a prepared mid-flow screen. Include the navigation and setup actions needed to reach the behavior being checked. Preserve real data and authentication; a fresh-load starting screen does not imply wiping user data. Explain any unavailable prerequisite briefly.

Before the first step, show a compact summary with the heading **Tutorial: <name of tutorial>**. Under **Steps:**, present the planned steps as a bulleted list rather than a paragraph or repeated tutorial name. Label any prerequisite or setup notes **Notes:** instead of “Before you start”; omit that section when there are no notes. Include **Go** and **Cancel** buttons. Go starts the walkthrough; Cancel dismisses it without executing tutorial actions or changing app data. Restart returns to this summary after safely resetting tutorial-owned state.

Each step has a stable identity, short title, one clear action where possible, expected result, target when applicable, and an observable completion condition when available. Keep visible text concise: normally one short action sentence and, only when needed, one short expected-result sentence. Put extra context behind optional details instead of making it required reading. Show only application state needed to judge the result.

Write instructions as direct actions naming the visible control and purpose: “Tap the Record button to start recording” or “Enter tempo here.” For value-entry steps, point to the input. For maximum flexibility, avoid naming a specific value or value type but it's okay to specify a valid range: for example, "Enter a tempo between <min> and <max> here:". Use the actual button labels and concrete tutorial values where appropriate, so the user knows exactly what to do.

- Display an info panel with step count and progress. For each actionable step, highlight the relevant control and point a tutorial arrow directly at it wherever possible; split steps with multiple targets into separate actions. Observation-only steps can point to the result being inspected. Keep the target usable and the panel readable. Update the arrow and highlight on scrolling, resizing, and layout changes independently of panel placement. Support keyboard controls, visible focus, and narrow screens without relying on the arrow alone.
- Users perform the application actions themselves. Advance automatically only after the intended action/result is detected; never advance on a timer. For results the tutorial cannot detect, offer explicit user confirmation. Remove previous-step listeners when navigating so stale events cannot advance another step.
- For actions that open an editor, dialog or route, arm completion detection from the user action and keep it armed through loading, rerenders and replacement of the clicked control. Observe the destination’s ready state through application state or a stable ancestor that survives the transition. Reset this evidence only on step navigation, Close or Restart. Keep arrow/panel positioning independent of completion detection so layout updates cannot reset the action or its observer. Advance exactly once when the destination is ready; button presses, loading shells and overlay movement alone are not completion.
- Value-entry steps advance automatically when the input contains a valid value and loses focus or the user hits return in the input - the value doesn't need to change. Observe input changes, including typing and paste, and the application's accepted value where relevant; avoid advancing on the first character or an incomplete intermediate match. Handle composed text after composition completes. Do not require Next, blur, or an extra tutorial confirmation to acknowledge entry. If the app requires Save/Apply to commit the value, guide that as a separate action step and verify its result separately.
- Choose a stable panel position when entering a step. Reserve an interaction area covering the target in both its normal and hover/focus states, any controls those states reveal, and the pointer path needed to reach them. Reuse the current panel position when it leaves this area clear; consecutive steps using the same area should not move the panel unnecessarily. If needed, scroll smoothly once to expose the area, then place the panel. Keep its viewport position fixed through pointer entry/exit, focus changes, playback state, rerenders, scrolling and temporary target disappearance. Recalculate placement on step navigation or viewport resize, or let the user drag it; retain a user-dragged position while it remains usable. A hidden target may hide the arrow or show recovery text, but must not reset the panel to a fallback position. When space is limited, use a fixed dock and scroll the application rather than moving the panel in response to hover.
- Controls used in the tutorial should be identified unambiguously with dedicated identification attributes, such as 'data-testid', for example: <button data-testid="open-training-annotation">
- Show names, values, and quoted text with a slightly different color and font from the tutorial text
- **Back** revisits instructions without undoing app actions. **Next** always allows forward navigation; movement alone leaves an unevidenced step unverified. **Skip** marks the current step skipped and advances. **Restart** clears walkthrough progress and automatically resets tutorial-owned test data where safe, then returns to the introduction. Preserve real app changes and explain any manual reset needed to restore the scenario.
- A simple **X** button dismisses the tutorial and leaves the app usable; give it the accessible name **Close guide**. **Reopen** restores the guide. Closing stops tutorial listeners and automatic advancement. Handle missing or hidden targets in the panel with concise recovery instructions and working navigation controls, rather than pointing at stale coordinates or blocking the app.
- When Back or Reopen returns to a step whose action has already happened, explain the current state and offer confirmation or a safe fixture reset. Do not leave instructions requiring an impossible transition from the current state.
- Provide **Not working** to record a failed expected result while allowing continued exploration. Maintain distinct observed, user-confirmed, failed, skipped, and unverified outcomes. Visiting a step or finding its target is not evidence that its expected result occurred. Back/Next preserve recorded evidence; revisiting a failed/skipped step can update it only with fresh evidence or an explicit user verdict. Initialize completion checks against current state so an already-satisfied condition does not create a cascade of automatic advances.

Use in-memory tutorial state by default. Finish with a per-step summary and **Copy report** containing the question, real-app versus simulation scope, useful reproduction context, expected results, outcomes, and limitations. Provide selectable text if clipboard access fails. Exclude secrets and personal data. Completion of the guide is not acceptance of a fix. Save reports, submit feedback, or change issue state only when separately requested.

## Verify and hand off

Exercise the generated walkthrough in the available browser: fresh-load starting state, summary with Go/Cancel, concise single-action steps and correctly targeted arrows, real target interaction, automatic completion, all navigation controls, failure and skip reporting, restart isolation, X/reopen, missing targets, scrolling/resizing, and keyboard use. Use safe disposable data. Check that Cancel leaves app data unchanged, manual navigation never manufactures verification, and restarting never reverts real app changes. Where browser or device access is unavailable, state the specific untested behavior.

For hover-revealed controls, record the panel rectangle before hovering, reveal the control, move onto it, and move away again. Verify unchanged panel position and an unobstructed target and pointer path in both states. Repeat with keyboard focus and playback state changes, including temporary target disappearance. Treat movement or overlap as a failed placement check, even when step completion works.

For steps that open another view, activate the real control and verify that the ready destination advances the guide exactly once without Next or a second click. Exercise delayed loading, control replacement and overlay repositioning during that transition; check that idle/background updates do not advance the following step. If this check fails, trace the action, observer lifetime and ready-state predicate rather than treating arrow movement as proof of detection.

For value-entry steps, check that incomplete/invalid input stays on the step and completing the requested value by typing or paste advances exactly once without Next or blur. Verify entry completion separately from any subsequent Save/Apply result.

Deliver the launch link/file or command, the question being demonstrated, and verification results with limitations. Distinguish tutorial checks, simulated behavior, observed real-app behavior, and the user's verdict. Preserve existing unrelated work; committing, publishing, or folding a disposable experiment into production follows the user's authorization and project workflow.
